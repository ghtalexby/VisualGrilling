# Attached ideas

An idea is a separate `kind:idea` node under root, with full `text`, five ordinary grades, `verdict`, chat and question descendants. Attaching an idea atomically queues its initial analysis, even without a connected agent; a repeated creation request does not duplicate it. Discussion alone does not start analysis. Users may explicitly select Analyze idea for reassessment; editing its text, grading a descendant answer, custom child creation and a changing reread trigger reassessment automatically. Never implement code as a consequence of an idea grade.

On `type:idea`, use `context` (including the full idea card), `title`, `brief`, `arch`, `reason`, and `capturedForSpec`. Read focus and related, scan the index for the same object or decision, and fetch every plausible match with `G node` before creating a question or claiming a decision is missing. Frozen events use only captured evidence as below. Images in delivered card chats are absolute file paths; open them directly with your image-reading tool. Do not move existing questions into an idea or duplicate questions already answered elsewhere. If sufficient evidence already exists, return a conclusion with no artificial questions. Discuss events with `scope:idea` remain reply-only (omit assessment); the full idea text is in `question`.

Return `{type:"idea",id,token,capturedForSpec,status,verdict,children?,audit?,semantics?}`. Echo the delivery flag and token exactly. Status must be `open|ok|weak|gap|verify`; verdict is a nonempty explanation up to 400 characters. Use the shared grading criteria in worker.md, evaluating material problems rather than percentages or the number of follow-ups. No active open/gap descendants is necessary for ok, but not sufficient: weak can remain the final conclusion. Verify means an untested assumption, gap no substantive solution. While questions need answers, explain what remains unresolved. Add up to four genuinely necessary questions, each with at least two options; zero is valid. An unresolved disagreement with another branch requires a user question before ok, never silently overriding an existing answer or relegating the conflict to a spec risk.

For `reason:edit`, audit every descendant question, including historical cards, using `{id,action:"keep|obsolete|restore|remove",reason}`. The audit is optional otherwise but, when supplied, must cover every descendant exactly once. Check question wording/options against the new premise. Preserve answered/discussed history: mark superseded questions obsolete instead of deleting or rewriting them. Restore a historical card only with a concrete reason. Remove only unanswered, undiscussed cards without merged history; explicitly remove their disposable descendants too or keep the parent. Conflict cards must be kept for the user to resolve. The idea transaction does not move questions; use the established whole-map reread when restructuring is necessary. All mutations are validated atomically.

`capturedForSpec:true` is a separate frozen evaluation. Use only supplied context or reads bound to `context.readToken` as in worker.md; never fetch live answers, chat or later idea text. Its result updates the frozen tree only; a separate live event may follow for the same idea. This is intentional, not duplicate work to skip. A stale result returns 409; return to the dispatcher. Never retry a stale token or start another waiter during apply.

Users may edit text during analysis; old analysis/discussion/answer deliveries affected by that premise become stale. Editing preserves history and requests a new audit. Deletion requires explicit UI confirmation, removes the whole branch and is blocked during work affecting it. Never work around that lock, delete files manually, or start implementation automatically.

# Codex file handoff

Hub-managed maps: preserve the supplied `hubEpoch`; include `--hub-epoch <captured epoch>` in every `G` command and copy it into every apply JSON, including notes and staged replies. On an epoch/Stop rejection, end this map loop; never claim or read a replacement epoch. Play preserves state and replays unfinished work; never initialize it.

Use `G wait --timeout 15 --inbox` or `G monitor --event <delivery> --inbox`. Pass the returned header (type, id, token, inbox path) to one fresh worker by default, without loading the full event in the parent. The opt-in reuse rule below is the only exception. Timeout stays inline. Do not use --inline for delegated work.

The worker reads session.md, inbox and current rules, checks identity, prepares ordinary apply JSON and writes UTF-8 without BOM to `<map directory>/result-<token>.json`. This is an authorized map-state write; never overwrite inbox/session. Run the local preflight below before returning a receipt. Return only `{type,id?,token,resultFile,workerSessionId?}` and optional bounded proposed notes; never echo the full result. Use separate token-specific files for multipart discussion, returning ordered paths. The main session alone applies each part; only the final part may rearm. On failure return a concise error; the parent inspects current work before fallback.

The parent keeps the expected token from the original header and runs `G apply --file "<resultFile>" --token "<expected>"` (add --rearm only in pure monitor). The CLI validates file size, inbox type/id/token and the expected token; the server validates current ownership and freshness. Failure results may use type failure with the same token. Do not apply a worker-supplied token without comparing it to the original header. Notes remain a separate ordinary apply notes operation. Use the selected waiting mode's ordering and do not rearm during preparation or multipart apply.

A 400 requires correcting the same result file; a 409 discards stale work under the mode's recovery rules. Keep token-specific files for diagnosis; never delete user map evidence as cleanup. Existing stdin apply and HTTP consumers remain supported.

If the worker's actual session UUID is available from its environment, copy it into optional top-level `telemetry:{workerSessionId:"<UUID>"}` in its result files. Otherwise omit telemetry; never guess or substitute the parent UUID. This is declared diagnostic attribution, not ownership proof. The server strips it before multipart validation; all existing token, epoch and parent-only apply/rearm rules remain unchanged.

## Worker preflight and compact templates

After writing the result, run `node "<skill directory>/result-preflight.mjs" --inbox "<inbox path>" --token "<original header token>" --file "<result path>"`. For multipart discussion repeat `--file` for every part in apply order in one invocation. Fix reported omissions in the same files, then rerun before returning the receipt. This read-only local check never applies, consumes, arms, edits files or fetches state. It checks file limits, event identity/epoch, captured scope, token, ordered complete multipart results, coverage shape and explicit ancestor intent. It cannot establish evidence truth, reference validity, current ownership or freshness; server validation remains authoritative. Existing HTTP/stdin clients retain their compatibility behavior.

Compact answer template (replace placeholders with actual evidence; never copy an invented reason or status):

```json
{"type":"answer","id":"<event id>","token":"<event token>","status":"ok","verdict":"<supported conclusion>","coverage":{"resolved":true,"reason":"<why evidence resolves the original weakness>","sources":[],"gaps":[]},"ancestors":[],"semantics":{"topics":[],"relates":[],"decision":"<evidence-based decision>","chatDigest":""}}
```

For weak/gap/verify use `resolved:false` and nonempty `gaps:[{gap,questionIds}]`; include `sources:[]` even without external evidence, or exact checked `{id,answer,contribution}` sources. Add `questions` only for missing clarifications (see coverage.md). Never auto-fill coverage or semantics to satisfy validation. Every grading entry needs coverage, including inline ancestors, discussion assessment/answers, followup and reread/reevaluate assessments. A reread audit's optional coverage uses the same shape.

For live answer and discussion grading entries choose exactly one of `ancestors:[...]` (empty only after checking) or `reviewAncestors:true` when required evidence is missing. Frozen answer results omit both; the frozen reassessment remains separate. Explanation-only discussion template: `{"type":"discuss","id":"<event id>","token":"<event token>","reply":"<explanation>"}`. Do not add grades when no evidence or judgment changed. Preserve `hubEpoch` on every result when delivered. For reevaluate, followup and idea, preserve the effective `capturedForSpec` scope: true selects frozen work; false or omission selects live work. Multipart intermediates contain only identity/part/more plus questions, links and/or answers; the last part carries reply and commands. No new semantic protocol fields are needed.

While a worker prepares, use interruptible waits of 45–60 seconds within the host communication interval, or verified completion notifications. Do not repeatedly poll at ten seconds. If still working at the communication deadline, give a meaningful update and wait again; do not create another map consumer or end the turn without verified wake-up.

Read one bounded section at a time. First inspect field names, counts and sizes; select complete relevant fields in small chunks. Batch independent small reads only within an explicit output budget. If output truncates, reread that section in smaller chunks before judging; never treat the truncated view as all evidence.

## Experimental worker reuse

`workerReuse.enabled` defaults to false. When enabled, the server includes a `workerContext` decision in the header and a complete revision manifest in the inbox. Start with a fresh child with no inherited conversation. Only when the header says `reuse:true`, its previous worker UUID matches the parent's completed child receipt, and the host exposes `collaboration.followup_task`, send the full new header and usual file/rule instructions to that same child with `followup_task`. Keep the local mapping from the compact receipt's actual workerSessionId to the tool's returned child target; a session UUID is not itself a collaboration target. Never call a host JSON-RPC endpoint directly. Missing capabilities, lost child identity after compaction, unknown measurements, or uncertainty mean a fresh child. Keep one worker, consumer and applier; only the parent applies, saves notes/reports and controls waiting.

The default limit is three successful events (configurable from one to five). Reuse is limited to consecutive live answers/discussions on the same question, with actual known worker input below the configured token limit and measured context-read amplification at most two. Header measurements cover protected API context reads only; filesystem/source reads remain unmeasured. Rotate on cross-branch or repeated API reads, unsupported work, frozen scope, nonfocus changes, policy/language/instruction changes, restart, cancellation, stale results or failure. Never estimate missing worker tokens from characters.

For every manifest-bearing event, fresh and reused workers reread the complete current inbox and current rules. Inspect all changed/removed IDs, discard outdated beliefs, and refetch external/file evidence before relying on it. Neither manifest hashes, previous replies nor summaries replace current evidence. Return exact top-level `workerContextAck:{deliveryToken:"<current token>",manifestRevision:"<current manifest revision>"}` with the result (also failures); only the final multipart part carries it. The preflight, file apply and server independently validate it. If a manifest is unavailable, the header explains why and requires a fresh worker; legacy disabled events need no acknowledgement.

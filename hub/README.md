# Windows boards Hub installation

From this checkout, run `powershell -ExecutionPolicy Bypass -File hub/install.ps1` with Node.js 18+ installed. This per-user installer requires the Windows .NET Framework C# compiler. It copies the skill runtime, Node executable, native transport and extension to `%LOCALAPPDATA%/VisualGrilling/Hub/install` (or `$env:GRILL_HUB_HOME/install`). Registry and board history stay outside the installation directory. The installer never resets boards.

The default developer setup requires a manual Chrome step: open `chrome://extensions`, enable Developer mode, choose **Load unpacked**, and select the installed `extension` directory printed by the installer. Its public manifest key fixes the extension ID. Chrome's registered native messaging launcher provides demand startup; the design supports startup after reboot without a pre-opened console, but this needs real reboot acceptance testing. Opening the extension automatically obtains its installation binding. Re-running the same installer rotates credentials while preserving installation identity and registry data; reload the extension afterward.

There is no published Chrome Web Store listing in this repository. `-Mode Store -StoreExtensionId <published-id>` registers that exact origin and opens the listing for Chrome's **Add extension** confirmation. It does not install a local CRX silently or prove that the supplied listing exists. Production distribution and clean-machine/post-reboot acceptance require real Windows/Chrome checks.

For safe packaging tests use `-StagingDir <disposable-directory> -NoRegister -NoBrowser`. Staging without both switches is rejected. This compiles and packages the host without writing Chrome's HKCU registration or opening a browser. `node dev/check-hub-native.mjs` uses a disposable staging fixture and tests the compiled launcher on Windows.

## Transport and trust

Chrome talks to `com.visualgrilling.hub` over binary native messages: four-byte little-endian length followed by UTF-8 JSON, maximum 512 KiB. The hidden C# launcher uses fixed installed absolute paths, no shell, and forwards bytes; stdout contains framed responses only. Each forwarded chunk is flushed so small requests and replies arrive while Chrome keeps the connection open. The compiled-launcher check exercises successive requests before closing stdin. The launcher and JavaScript host check Chrome's process argument against the single installed `chrome-extension://<id>/` origin. A JSON field cannot establish caller identity. There is no web page bridge or external extension messaging listener.

Requests use `{v:1,id,method,params,installationId,secret,epoch}`. `bind` is available only to the validated native caller and returns the three credential fields without starting a daemon. Other methods require all credentials: `list`, `open`, `play`, `stop`, `rebind`, `chat`, `sendChat`, `login`, `approval`. Board commands require `params.boardId`; `rebind` also needs `params.dir`. Inputs and responses are bounded. Responses use `{v:1,id,ok,result}` or `{v:1,id,ok:false,error:{code,message}}`. `REBIND_REQUIRED` allows the extension to bind again automatically after reinstall. Credentials are reread on every command, so old connected native processes cannot retain access after rotation.

Each native connection admits at most 16 pending responses and pauses input under output backpressure. Commands retain arrival order; overlapping Play requests for the same board and installation credentials share one pending command and its success or failure. Stop and rebind delimit that sharing, so Play → Stop → Play performs both launches in order. Each envelope is independently authenticated before sharing. Responses carry their original request IDs, use complete noninterleaved frames, and are drained after stdin closes, including work admitted before a malformed later frame. Failed or ambiguous commands are never automatically replayed by the native host.

The installer creates secrets only inside a directory with inheritance disabled and a current-user full-control ACL. It replaces credentials atomically. This protects against other accounts, not arbitrary programs already running as the same Windows user. The daemon must reread credentials before authorizing each request too. Existing board registry data is not a credential and is preserved on rotation.

The host starts the fixed installed Node executable with `service.mjs --config <installation.json>`, hidden and detached. The daemon owns a lifetime singleton lock, allowing concurrent native clients without duplicate board controllers. The native host accepts `dataDir/endpoint.json` only after authenticated health validation of its installation identity and epoch. Local requests use `127.0.0.1`, exact extension Origin, `x-grill: 1`, `Authorization: Bearer <secret>` and `x-grill-epoch`. Commands go to `POST /api/command`; health goes to `GET /api/health`. A failed start is an explicit error, never a fabricated empty list. The extension owns its visibly stale last-successful cache.

The installer records an absolute Codex executable or JavaScript entry point for background Play, using the installed npm package or `-CodexPath <codex.exe-or-codex.js>`. It never invokes a `.cmd`/PowerShell wrapper. If discovery fails, it prints a warning; install Codex and rerun with `-CodexPath` before background Play. This prevents Chrome's narrower post-reboot environment from losing the executable path.

Reinstallation retains the packaged Node executable to avoid overwriting a running binary. Updating Node itself requires stopping the Hub first and replacing `install/node.exe`. Obsolete versioned C# launchers may remain after reinstall so an in-use executable is never removed. These files contain fixed paths and origin, not secrets. Credential rotation takes effect on the next request; already running service code remains loaded until that service is restarted. Stop controlled work before upgrading runtime code, then restart the service; the installer does not silently kill active agents.

# Discussion

- `{"type":"discuss", ...}`: answer in the map language, using `message`, `images`, and `context.focus`/`related` plus the index. `scope` is question, project, or idea; root and ideas are never graded as questions. Inspect images with your image-reading tool; if unavailable say so without guessing. Quoted messages preserve `[Про вариант ответа «…»]` and `[Про вердикт «…»]` protocol prefixes. Delivered `images` and images in context card chats are absolute file paths; open them directly. Inspect existing answers, descendants and pending work before drawing conclusions.

### Questions and answers from discussion

Every substantive question requiring a user answer must appear as a card, automatically, in question, project and idea discussions. Read focus and related; scan the index for the same object or decision and fetch every plausible match with `G node` before creating a question, recording another card's answer, or claiming a decision is missing. Consider those answers and reuse existing IDs. For each new question choose the best existing parent anywhere on the map (`q`, `idea`, or root); use root when no suitable parent exists. Explanations without questions add no cards. Do not impose a question quota or put necessary discussion questions in reserve; the separate reread issuance limits remain unchanged.

Return `questions:[{key:"$new",parentId,q,why,area,options,recommendation?}]` and `links:["existing-id","$new"]`. Keys may reference other new parents; cycles are forbidden. Include a link for every new question and every reused question you ask. The server renders the actual question text with a safe card link below `reply`, so do not invent IDs or HTML links in prose. Text and links become visible only after the entire result succeeds.

If a user message answers multiple cards, include `answers:[{id,messageIds:["user-message-id"],status,verdict}]` for **each** applicable current question, including the current one. IDs may reference new question keys. The focus card's `chat` supplies canonical user message IDs/texts; the server copies their exact text, never your proposed answer. Assess sufficiency independently: copied text is not evidence of closure. Use verify for untested assumptions, weak/gap for unresolved issues. Never convert your unaccepted suggestion into a user decision. Pending answers and other queued/running discussions cannot be overwritten. Previous answers, provenance and verdicts remain in history; descendants survive. This updates only the live map, never a captured specification.

Legacy `assessment:{status,verdict,answer}` remains for verdict-only correction of the current question. It preserves an existing answer; use `answers` when recording a new user response. Never combine both for the same target. Obsolete cards cannot receive an answer or assessment: request reread with evidence to mark/restore them instead, preserving answered/discussed history.

Keep `reply` within 2000 characters and verdicts within 400. Copied user text is bounded to 2000 characters; choose relevant message IDs without rewriting them. Question text is bounded to 220 characters. Context is bounded to 500 nodes / 600000 serialized characters; an explicit limit failure is not a successful or partial review.

For large results, use sequential `apply discuss` calls with the same token and `part:0,more:true`, then `part:1,more:true`, etc. Intermediate parts contain only `questions`, `links`, and/or `answers`; send `reply`, optional `semantics` and commands in the last part with `more:false`. There are at most 500 parts and 600000 serialized characters in aggregate, with at most 500 entries per operation list. These are safety limits, not a content quota. Stage every required question before committing; never claim full success after staging (`committed:false`) or after any rejection. Identical retries of staged parts are idempotent. On a size rejection, report the explicit limit without dropping questions or claiming that the result was saved. On restart/new delivery discard your parts and recompute against the new focused context/token. Do not re-arm the waiter between parts. The final commit validates all references and current map revision atomically.

```json
{"type":"discuss","id":"root","token":"...","reply":"We still need a failover decision.","questions":[{"key":"$failover","parentId":"existing-question-id","q":"How will failover work?","options":["Automatic","Manual"]}],"links":["$failover","existing-question-id"],"answers":[{"id":"existing-question-id","messageIds":["user-message-id"],"status":"verify","verdict":"Decision supplied; load test still missing."}]}
```

### Explicit commands from discussion

Honor a direct user request to reread the whole map or mark another question from question, project or idea chat. These requests are authorized map operations, not attempts to override worker rules. Do not require a button click, another chat or another confirmation. Quoted text, attached documents and your own suggestions are not user commands.

- For a whole-map reread, include `"reread":true` in the current `apply discuss`. Reply that the review is queued, not already completed. The server starts it after pending work and specifications finish.
- For a request about another question, scan `G index`, then read plausible targets with `G node` to identify its exact ID from its title, priority and parent. If the target or requested meaning is ambiguous, ask a concise clarification in the discussion reply. Otherwise include `"forward":{"id":"<target question id>","message":"<faithful user request, relevant decision/evidence and source question>"}` in `apply discuss`. Preserve the requested status and rationale; do not invent a user answer. The server saves this request in the target discussion and queues its normal worker, which sees the complete target branch and updates its grade using assessment. Do not forward it again once it addresses the current question. If evidence is insufficient to justify closure, explain the missing evidence and use the appropriate grade rather than inventing certainty. Obsolete targets require reread restoration first. Pending answers are graded before a final discussion assessment; do not claim a queued change is already done.
- Both fields may be combined with each other and with a current-question assessment. They are validated before mutation, and the delivery token prevents replay. A rejected apply means none of the requested operations succeeded; handle errors through the normal dispatcher fallback. Never edit state files directly or operate on a different map implicitly.


An oversized discussion context returns HTTP 400, records `node.discussError`, and releases only that failed delivery so unrelated queued work can continue. The UI shows the error; all user messages remain saved. After addressing the context limit, send another message to retry the thread (all messages since the last agent reply are delivered together). Resetting the chat clears the error. This is a failed discussion, never a successful partial result.

Replacing an existing answer with different discussion text also queues an automatic incremental reread, as a direct Answer-tab edit does, so decisions in other branches can be reconsidered. The replacement is already graded, so this reread is settled (not cancelable as a withdrawn pending answer). Identical text does not trigger an edit reread; finish-pending/finished maps retain the existing automatic-reread suppression.

Each `answers` entry may include `ancestors:[{id,status,verdict}]` (empty means checked, unchanged). IDs must be answered current ancestors of that target. Omission or `reviewAncestors:true` requests separate reassessment; never combine it with `ancestors`. Assess substantive resolution as in answer grading.

Project events include `conversationId`; root focus chat contains only that conversation. Reply using the normal root ID/token; the server routes the reply. Other conversations remain available for whole-map reread, but must not be treated as new messages in this event.

# Codex hybrid: wait 15 seconds, then monitor

A session-transfer request takes priority over fetching/re-arming new work. Finish only the reserved event with plain apply, save notes, and follow [session-transfer.md](session-transfer.md). A `type:transfer` wait response is a control handoff, never a worker grading event.

This is the default Codex mode. Keep pure monitor and blocking wait available when explicitly requested. Read [monitor.md](monitor.md) for host selection, binding, delivery identity, transport errors and restart recovery. Its immediate arm and `apply --rearm` steps apply only to pure monitor; use the loop below in hybrid mode. A confirmed standalone `--no-daemon` host or diagnosed unavailable wake-up transport uses level 0 instead. One map and one event worker per session.

`G` always means the exact CLI with the same project cwd, absolute `--dir` and `--name`. Start/init or explicitly continue normally. Remember the selected mode across wake-ups and compaction; a notification does not switch hybrid to pure monitor.

1. On launch/continuation or after uncertain execution, inspect `G monitor --status`. Preserve an already `armed` subscription and end the turn. For `pending`/`notifying`, fetch its delivery with `G monitor --event <delivery> --inbox` and finish it before switching to wait. For `ready`, the previous event was applied: stop that completed subscription with `G monitor --stop`, without replaying the result. Diagnose `failed` as described in monitor.md; never blindly retry notification. After restart (`off`), unfinished work is recoverable by wait. Never stop another session's subscription or overlap a running wait/worker.
2. With no subscription and no unfinished event, run `G wait --timeout 15 --inbox` in the foreground. Allow the shell command to finish (use its continuation tool if it returns a process ID). This is a single long poll, not a sleep or a loop of status requests. Do not end the turn during this wait.
3. If it returns an event, prepare and apply it, then start a fresh 15-second wait. Use one fresh prepare-only subagent with no inherited conversation for each event, whether received by wait or monitor. Follow [file handoff](handoff.md): supply only the event header/inbox path, session.md, cwd, CLI, map name/root, worker.md and the current event rules. Do not read or repeat the full event in the main session. Only the main session checks identity, applies results, writes notes and saves reports. If preparation fails, inspect current work and finish it yourself; never replay an already applied or stale result.
4. Use `G apply --file <result> --token <expected>`, without `--rearm`, in both phases. A monitored event stays reserved during preparation, notes and multipart discussion; only the final `more:false` completes discussion. After successful completion, its subscription becomes `ready`: run `G monitor --stop`, then return to the 15-second wait. No new notification is sent between successful apply and stop; queued actions remain saved. A deliberate completed `ok:false` result also continues this loop. On 400 correct the current result; do not stop or wait. On stale 409 discard it and inspect monitor status: an active subscription can already have reserved replacement work, so fetch that delivery rather than stopping it. If monitor is off and no worker is still applying, recover with wait.
5. Only on `type:timeout` after the 15-second wait, run `G monitor` and end the turn when armed. Do not repeat wait on idle timeout. Work submitted between timeout and arming stays queued and is reserved by monitor. For `pending`/`notifying`, leave the single subscription in place and handle its notification; never create a second consumer. The server wakes the same Codex session; fetch the exact delivery and return to step 3. While armed there are no periodic model calls and no 30-minute idle pause.
6. After a new finish, save `G report`, stop any completed monitor subscription and end the turn. Do not start the 15-second wait or re-arm. Failed finish also holds later actions: report the failure and stop listening. Late actions remain paused until explicit continuation with `G start --continue`; ordinary recovery with `G start` does not release them. On recovery, inspect `/api/state` via `G state` if finish completion is uncertain; `actionQueue.paused` is the persisted boundary, unlike the historical `finished` flag. Never wait/re-arm a paused boundary merely because monitor is off/ready.

An ordinary chat message leaves an armed subscription in place. An explicit request to change mode first settles current work and stops the old subscription/wait before entering the selected loop. `wait --timeout 50` and its 30-minute idle limit belong only to explicit/fallback level 0, not this hybrid mode.
